## Delivered behavior

- Requirements belong to exactly one Project and receive immutable, per-Project keys (`REQ-001`, …);
- controlled Priority, DecisionStatus and SourceType vocabularies with independent semantics;
- new Requirements start Proposed; Deferred and Rejected retain a mandatory reason;
- persistently ordered Acceptance Criteria, including optional verification references, and at least one criterion for Must Requirements;
- Project and Requirement references use the eleven controlled types and explicit `ProjectId` plus optional `RequirementId` ownership;
- centralized same-Project checks for ownership, source references and verification references;
- centralized target and obvious-secret validation, revalidation before opening, HTTPS-only web targets and typed GitHub URL validation;
- missing local targets and invalid targets return understandable failures without deleting reference data;
- native German WinForms workspaces for Requirements and references with menu/primary navigation, F1 glossary, tooltips, keyboard access and accessibility metadata;
- no hard delete for Requirements and no task, workflow, provider API, automatic link checker, document-management or 0.4.0 functionality.

## Database, migration and recovery evidence

Current schema: `202608200003_RequirementsAndTypedReferences`.

The additive EF Core migration creates `Requirements`, `AcceptanceCriteria` and `ExternalReferences`,
their foreign keys and lookup indices, and the authoritative unique constraint on `(ProjectId, Key)`.
It does not recreate or destructively transform the accepted 0.2 tables. The real-SQLite migration test
constructs the 0.2 physical schema and history, inserts existing Project, steering and blocker facts,
migrates to 0.3, verifies their preservation, saves Requirement/reference facts and reopens them through
new service instances.

The persistence suite also verifies Requirement key allocation, stable keys, criterion order/round-trip,
same-Project rules, stale-write conflicts and missing local targets without data loss. The recovery suite
passed with the new schema for backup, checksum/schema/integrity validation, staged restore, rollback and
negative replacement paths. Pre-migration backup behavior remains part of `DatabaseMigrator`.

## Dependencies, limitations and debt

- No new direct NuGet dependency was added.
- References remain manually maintained; HTTPS targets are never prefetched and no provider authentication,
  token handling, provider API or background reachability state exists.
- Requirement/reference lists are loaded per Project without speculative paging or caching; measure realistic
  data before optimization.
- Concurrent key allocation is protected by the database unique constraint and returns an observable conflict;
  the local single-user UI can retry creation explicitly rather than hiding a collision.
- Physical-monitor DPI, visible shell opening, normal packaged shutdown and endurance remain manual checks.
- UI strings can move to `.resx` when localization is scheduled; German-only 0.3 does not require that work.
- No known data-loss, recovery, security or architecture defect remains open.

0.4.0 search, portable exchange and relationship navigation were not started.
